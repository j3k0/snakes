# v15 design review — scope and risk (reviewer 1)

Independent subagent, 2026-11-14. Read `v15-design-plan.md` in full; skimmed `v15-ideation-context.md`. No code, tests, git, or production traffic. Lens: scope, risk, ordering.

**1. BLOCKER — Ten features is too large, and the drop order is wrong at position two.**
For a game with zero measured players, the decidable release is the one that makes the door passable and the funnel readable: F1, F2, F3, F4, F6, F7, F10. Cut two now, not conditionally. **F5**: the unreachability is real (25 taps opened nothing) but nothing in the evidence says a first-visit player needs Quests or Cosmetics in ten seconds — and the plan's own "other four panels stay keyboard-only" concedes the line is arbitrary; it defers to v16 with everything else meta. **F8**: M-sized, and it serves a path with zero lifetime exercise — `K` is unreachable, no run has ever been finished, so no challenge link has ever been sent or received. The pre-declared order (F5, then F9, then F4(a)) gets position two backwards: F9 is S-sized and the only feature aimed at JC's posts — the sole traffic source and the start of the 30-day judgment window. Cutting F9 saves almost nothing and degrades the exact event the cycle is measured by; F8 is the M-sized cut that actually saves a release. Two consequences travel with the cuts: F7's Share is defined by F8's link format, so Share goes with F8 (F7 ships as the tap-guard alone — the guard fixes the measured reflex-tap bug); and context fail-today tests 5 and 6 move to the deferred list with their features, so acceptance item 1 is amended, not silently failed.
**Required change:** cut F5 and F8 from v15 now, strip Share from F7, defer context tests 5/6 with them, and set the remaining drop order to F4(a) before F9.

**2. BLOCKER — F4's 250 ms window guards a gesture this page cannot produce.**
The body is `100vh; overflow: hidden` — there is no content to scroll, so the "scrolling visitor" is a fiction. The realistic accidental gesture is pull-to-refresh or an address-bar drag, and those are displacement-discriminated, not time-discriminated: a 400 ms downward drag passes a 250 ms window and starts the run. Tap and swipe overlap in duration; the swipe handler already owns a displacement threshold, so reuse it (moved past the threshold = swipe, never a start). Pull-to-refresh is properly a CSS fix (`overscroll-behavior-y: contain`). The cost side also barely bites: this overlay appears once per device, the default mode (not daily) is selected, and returning-visitor idle taps already start runs today (context fact 1, tap 2) — F4 unifies the overlay with existing idle behaviour, it does not open a new hazard. Ship tap-to-start; the AGENTS.md reversal in the same commit is already promised and is right.
**Required change:** replace the 250 ms window with the swipe handler's existing displacement threshold plus `overscroll-behavior-y: contain`, and delete the scrolling-visitor rationale.

**3. BLOCKER — F2 must be scale-only, and its gate misses the viewport changes phones actually produce.**
F3's "below the F2 clip line" is clip-thinking: if any implementation clips, rows hide again and the feature defeats its own gate. Say scale, once. The gate covers four static sizes but no mid-session case: URL-bar collapse changes `window.innerHeight` during play (the measured-chrome calculation must re-derive per resize, and F3/F7 tap bands must re-map), rotation does the same violently, and desktop zoom or a shrunk window crosses the 700 px `compact` threshold — all in the first session on the target platform. Narrow the payload too: hiding `#score`/`#highScore` during play removes the live score from a phone; hide `h1` alone unless the cap fails the 320×568 gate without it. Finally, F3's gate asserts contrast and a centre-tap but no minimum physical size — at a ~0.8 scale a 44 px band is ~35 physical px.
**Required change:** state F2 as scale-only; add gate cases for URL-bar collapse and rotation mid-play (board fully visible, bands still hit) and a minimum physical tap-target assertion for F3.

**4. SHOULD — F6's seed invalidation is fair, but only if the cut-over is recorded where baselines are read.**
"No players are affected" is true and this is the only window the board could be fixed for free — daily, diary, and ghost data are all local-device, so no stranger history exists to invalidate. But the funnel's purpose is a pre/post read, and post-v15 `die_obs` in run one should drop by design. If the deploy date is not recorded as a board-generation cut-over, the first funnel read attributes a board change to a UX change.
**Required change:** record the v15 seed-mapping cut-over date in F10's report format and the shared reports before deploy.

**5. SHOULD — F1-first holds, but for the descoping reason, not the judgment reason; and the funnel's load-scoped semantics are unstated.**
For: the counters are the release's insurance — a descope (finding 1) that dropped them would make the cycle unjudgeable, and landing F1 first makes it structurally uncuttable. Against: all ten features deploy together, so commit order cannot create pre/post attribution — the funnel only ever sees the post state. Verdict: keep the rule, with an honest reason. Two unstated semantics will otherwise be misread in F10's rates: keys are once per page load (five runs on one visit = one `start`, one `first_food`, one death bucket — the first), and a Zen quit (`endZenSession`, no death) leaves a `start` with no death key, which must not read as "still playing". F4 also redefines `overlay_gone` (same tap as `start`).
**Required change:** keep F1 first, and write the load-scoped key semantics, the Zen-quit gap, and an F4-lands re-run of F1's gate into F1/F10.
