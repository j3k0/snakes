# Snakes v12 — Implementation Plan Review

Scope: `IMPL_PLAN_v12.md` (273 lines) against `snake.html` @ master `23a427e` (8594 lines, working tree clean, 8 untracked v12 docs). Every anchor the plan names was opened and checked; anchors not cited here verified exactly as written. All line numbers below are `snake.html` unless prefixed `PLAN:` (`IMPL_PLAN_v12.md`).

## Verdict

**Approve with changes.** The plan is unusually well anchored — of ~120 cited line numbers, all but six resolve to within ±2 lines of the named symbol, and the enumerations that the two design reviews blocked on (7 saves / 10 deaths, the food-award site list, `L6030`, `L5850`/`L5873`) are now exactly right. It closes 8 of the 11 distinct prior blocking issues outright; three (the `doubleGold` arithmetic, the assertion budgets, the pre-cascade raw score) are only partially resolved — see the closure table. It is **not yet executable as written**: one flagship acceptance number is arithmetically unreachable (would block step 6's gate or induce a wrong hook), one step-6 acceptance criterion is unconstructible, one session-end wiring requirement violates the plan's own invariant, and one new cadence hook is ordered below its consumer.

**Single most important fix:** correct step 6's exact-delta acceptance numbers and state their preconditions (PLAN:174-175). `180` is unreachable under *any* placement of the `doubleGold` multiplier — with `golden_food` drafted, `pigmentRushActive` sets `effectiveHoardMult = 2`, not 3, so the correct delta is `10 ×2 ×3 ×2 = 120`. An implementer who trusts `180` either writes an assertion that cannot pass (stalling the pass-1 gate, which blocks step 7) or moves the multiplier into `addScore` to manufacture the number — the exact regression both reviews blocked on.

## Technical claim checks

**C-1 `invertControls` axis-swap safety.** The stated proof is **false as written**: "(dy,dx) = (−dx,−dy) … forces both to zero" (PLAN:195). `dy = −dx` is a *single* equation and is satisfied by `dx = 1, dy = −1`; that input swaps to `(−1, 1)`, exactly the reverse of `(1,−1)`. The conclusion is nevertheless safe today, for a reason the plan does not state: both callers emit axis-aligned unit vectors. Keydown builds `(±TILE_SIZE,0)/(0,±TILE_SIZE)` with exactly one non-zero component (the switch at L8305-8325), and swipe does the same (L8491-8495). A swap of an axis-aligned vector is its perpendicular, never its reverse, so the reverse check at L4057 is never the thing that saves the player — the input domain is. Traced the four inputs with `activeMutators=['gravity','mirror']` and the window open while moving right: Left→up (queued), Up→duplicate (rejected), Right→down (queued), Down→reverse (rejected); no 180° is reachable. **Stationary head:** irrelevant — `gravity` forces `dy = ±TILE_SIZE` whenever `dy` is not already vertical (L6417-6420), and `resetGame`/`restoreFromSnapshot` both guarantee a non-zero `(dx,dy)` (L2221, L2837). **Wrapping:** irrelevant, the swap maps direction vectors, not positions. **Queue already holding entries / cap of 2:** irrelevant — swap and mirror both apply to the incoming press before the shared tail comparison, and the cap (L4061) only drops presses. **One consequence the plan does not state:** the swap makes one of the four presses a no-op (it maps to the reverse) — expected, but it means "press all four directions" is not four turns.

**C-2 The mirror flip must precede the reverse check.** Verified and unchanged by the move. Previously the flip ran in the keydown handler at L8332 *before* the L8335 call, so `setNextDirection`'s check already saw the flipped candidate; moving it to the top of `setNextDirection` preserves that. All three paths traced: keyboard (L8335 after the switch's `default: return`), D-pad (synthetic `keydown`, L8341 → same handler), swipe (L8499, no flip before this change — the shipped bug). The only behavioural delta is the intended one: swipe now flips. Non-mirror runs are bit-identical.

**C-3 `chaosCycle` as an additive gate.** The wording does guarantee it: "an additive gate `resonanceActive && cycleAllows(name)` … **Never** a replacement of the existing mutator checks" (PLAN:167), and `detectResonance` sorts and joins the full set (L897-899), so a subset drafter can never satisfy `gravity~mirror~phase_shift`. However the *acceptance* (PLAN:179) is unconstructible: "the three mutators drafted **without** the resonance" cannot exist — drafting all three **is** the resonance. See **B-2**.

**C-4 `doubleGold`/`feastFamine` site enumeration.** **Complete and correctly bounded.** Every `addScore`/`awardXP` call in the file was enumerated: food sites L6901 (XP), L6925, L7054 (echo `food2`, `addScore` only), L7077-7078 (portal twin, score **and** XP), L7113 (hoard bonus, `addScore` only). Deliberately excluded and correctly identified: combustion L6928, combo bonus L6941. Correctly absent from the list: the bomb path awards nothing (`bomb.pts = 0`, `xp = 0`, L1300, and the branch at L6804 skips all awards), the extraFoods branch has no XP award, and non-food funnels (bounty L3566-3567, quest L1543, achievement L7543/7558, daily L7600, survival drip L6496, session-end L3329/L3401) are outside the descriptor's scope. `doubleGold`'s descriptor is therefore made true. **But the acceptance numbers are wrong** (**B-1**), and the "pins the placement to the food site" claim is false: for both the 60 and the pigment case, a funnel-level ×2 on `totalMult` produces an identical number, so no assertion in the plan can distinguish the two placements. The discriminating assertion is a **non-food** award (e.g. `addScore(bounty.pts)` at L3566 must stay undoubled).

**C-5 Step 5 raw-score capture and ordering.** Correct. `gameOver()` overwrites `score = Math.floor(score * cascMult)` at L3322 and calls `buildRecapData()` only at L3346, so the capture window between them is valid and `score/0.5` really is unrecoverable. **But `updateScoreDisplay()` writes `modeHighScores` from the raw score on every `addScore`** (L2290-2294, called at L1862), and `finalizeSession()` writes the *post-cascade* value only if it beats the stored best (L3293-3296) — so the persisted and displayed "Best" is the raw score while the card headline is the final score. A cascaded run can render `Score: 500` next to `−500 vs best` where the 1000 was set by that same run. The plan's disclosure step says nothing about this (see N-8). And because `endZenSession()` also builds the recap (L3418), the capture must be wired there too, where the cascade is never applied (L3397) — **B-3**.

**C-6 Step 4 save/restore depth assertion.** Implementable without the deferred general guard: it is a test-local monkey-patch (`page.evaluate` wrapping `ctx.save`/`ctx.restore` around one `drawGame(1)`), no production code. It **does** catch the v11 class that matters here — a leaked `save` (early return / misplaced `restore` / loop `continue`) makes the net depth non-zero at the end of the call, which the assertion reads directly. It does **not** catch an unbalanced *transform* (`translate`/`scale`/`setTransform` with no save), and all new drawing in step 4 sits inside the existing L4806/L4824 pair, so the scope is proportionate. Two caveats: the assertion covers only the pair the new code uses (the pre-existing adjacency pair L4833/L4840 is not exercised unless `hazardAdjacentThisTick && hazardChainStreak > 0` with an on-phase hazard 1 tile out), and it is narrower than the design's own requirement ("over a run long enough to include on→off→on transitions", PLAN-companion v12-design-plan B7).

## Ordering and ownership

- **`resetGame()` (steps 1, 5, 6) and `setNextDirection` (steps 2, 7): safe as ordered.** Step 2 lands the mirror line that steps 6 (gate) and 7 (suspend flag + swap) edit; step 5's `lastSaveEvent` reset (L2137) and step 6's counter resets are additive to the same function. Every step re-runs the full suite (PLAN:33-36), so the step-2 assertions live in `test-v12.mjs` and are re-executed after steps 6 and 7 mutate the same line — that is the property that makes the ordering safe, and it is worth stating explicitly.
- **One real ordering defect:** step 6's `intangiblePhase` hunger skip targets L6433, which executes *before* the resonance block at L6462 where `tickResonance()` is specified to live (**B-4**). `hungerInterval()` (item 5) has the same consumer-before-producer shape but is trivially fixed by computing from `activeMutators` inside the helper.
- **`showFoodLegend` (steps 1→3): safe.** Step 1 changes only the delivery path, step 3 only the string; step 1's acceptance (three messages in order) survives step 3.
- **No step invalidates a previous step's verification beyond re-running the suite.** Step 7's seeded `shuffleFoodWeights` changes the RNG stream for `chaos_seed` runs, but no earlier step's acceptance depends on food positions (step 6's deltas force the tier).
- **Missing from the ordering section:** the plan has no explicit "re-run the previous step's acceptance after editing a shared function" line. Given `resetGame` ×3 and `setNextDirection` ×2 it should be one bullet in the global contract.
- **Snapshot and determinism checks exist but are per-step, not in the global contract.** Step 6 has the pre-v12 snapshot restore (PLAN:181) and step 7 the determinism diff (PLAN:204). Nothing else adds snapshot fields (steps 5 and 8 add none), so this is adequate — but the design's Verification §5/§6 were global and are now only findable inside step 6/7 acceptance lists.
- **Ownership of AGENTS.md is fine** (cleanup), but it is the only doc update; the in-game help overhaul in step 3 and the AGENTS.md "Input Buffer Queue" rewrite are consistent with each other.

## Blocking issues

**B-1 — `180` is unreachable; `60`/`50` lack their preconditions (PLAN:174-175).** With `doubleGold` active and `pigmentRushActive` set, `addScore(20)` does `amount = 60` (golden ×3, L1846-1847), then `effectiveHoardMult = activeMutators.indexOf('golden_food') !== -1 ? 2 : 3` → **2** (L1853-1855), `totalMult = min(1×2×1, 4) = 2`, `score += 120`. `Chaos Gold` necessarily drafts `golden_food`, so `180` requires `golden_food` absent — impossible for this resonance. It is unreachable under an `amount`-level or `totalMult`-level hook too, so the stated number cannot be reached by any implementation. Separately, `60`/`50` hold **only** if `comboCount === 0` at the award, i.e. the run's first eat: the eat path sets `comboCount = min(50, comboCount+1)` inside a 3 s window and otherwise to `evolutionTier >= 3 ? minCombo : 0` (L6869-6874), and any `comboCount > 0` adds `addScore(Math.floor(comboCount*2))` at L6941 (with `golden_food` that is +6, not +2). `sessionXP` is also polluted by the survival drip `awardXP(1)` on every `gameTick % 10 === 0` (L6496) and by `awardXP`'s streak multiplier (L7392). *Fix:* assert `120` for the pigment case; state the preconditions explicitly (run's first eat, `evolutionTier < 3`, no combustion brew, fresh profile: streak 0 / level < 20 / `pinnacleRank` 0, and choose a tick with `gameTick % 10 !== 0`); and replace the "pins the placement" claim with a non-food award assertion (bounty at L3566 must be undoubled).

**B-2 — The Chaos Theory acceptance is unconstructible (PLAN:179).** `detectResonance` keys on the sorted full mutator set (L897-899) and `gravity~mirror~phase_shift` is that key, so "the three mutators drafted **without** the resonance" describes no reachable state: drafting the three *is* entering the branch. The item that actually verifies the additive-gate property is a **subset** run. *Fix:* rewrite as "draft `['gravity','mirror']` (subset, no resonance) and assert the gravity block still fires on its normal cadence" — that is the invariant the plan's own protective comment (PLAN:167) claims.

**B-3 — The raw-score/cascade capture is not wired into `endZenSession()` (PLAN:137).** `buildRecapData()` is called from both session ends (L3346 and L3418), and `endZenSession()` funnels through `finalizeSession(true)` after `score = snake.length` (L3397) — it never applies the cascade. Zen is draftable (`if (draftModeEnabled && unlockedMutators.length > 0 && gameMode !== 'daily')`, L7924), so a Zen run with 2-3 mutators is reachable. Following the plan literally gives `buildRecapData` a `cascadeMult` derived from `activeMutators.length` (= 0.5) and a `rawScore` that is either stale from a previous Classic death or undefined — i.e. the card renders a false `Cascade ×0.5 raw → final` row on a score that was never halved, and the diary (`saveDiaryEntry`, also called from Zen at L3421) inherits nothing. This also violates the plan's own global invariant ("Session-end logic goes in **both** `gameOver()` and `endZenSession()`", PLAN:22). *Fix:* capture/reset `sessionRawScore` (and set `cascadeMult = 1`) in both paths — e.g. compute `cascadeMult` only where the multiply actually happens, and default `rawScore` to `score` otherwise.

**B-4 — `intangiblePhase`'s hunger-skip hook is ordered below its consumer (PLAN:161).** `hungerTickCounter++` is L6433, inside the block at L6427-6444; the resonance block whose replacement (`tickResonance()`) is specified "where the current resonance block sits" is L6462-6474, and `activeResonance` is (re)computed there at L6462.
