# Snakes v12 — Design Plan Review 1

## Verdict

**Needs rework on Feature A; the other five features are approvable with edits.** The plan's inventory of the shipped code is mostly accurate and unusually well-read (line numbers for `RESONANCES`, `drawHazards`' save/restore pairs, `cardH`, `foodColor(Object.keys(FOOD_TIERS)[i])`, `modeY`, the help overlay's 40%/15% and 10-row controls table, `toastQueue`'s never-cleared/unbounded state, and the 129-assertion/11-suite baseline all verify exactly). But two of the flagship's four stated acceptance criteria are arithmetically impossible against the code they describe — `addScore(100)` under Chaos Gold + hoard is **450 today**, not `≤400` (plan L52; proven by `test-v9.mjs:221-229`), and the invert catch "queued dx must be `+TILE_SIZE`" (plan L49) cannot hold, because the resonance that owns `invertControls` is `gravity~mirror`, so the mirror flip always composes with the inversion and cancels `dx` before the reverse check. A third premise — "the only resonance-era `Math.random()` call in the tick loop" (plan L23) — is false: `shuffleFoodWeights()` (L6030) uses `Math.random()` and is called from the tick loop at L6456-6459, and the plan *doubles that call rate*. The single most important thing to fix: Feature A's per-effect specification for `invertControls` and `quantumToggle`, both of which are shipped-inert no-ops as written — the exact v11 failure mode this cycle exists to prevent.

## Blocking issues

1. **`doubleGold`'s acceptance assertion is false on master, and its "cannot compound past ×4" premise is wrong.** Plan L31 and L52. `addScore` multiplies `amount` by 3 for `golden_food` at L1846-1847 — i.e. *before* `totalMult` is computed — then caps only `multi * effectiveHoardMult * hazardChainMult` at 4 (L1860). So `addScore(100)` under Chaos Gold + hoard is `100→300→×1.5 (L1856 clamp)→450`, not `≤400`; `test-v9.mjs:221-229` already asserts the 45-for-10 case. An implementer following the plan would either rewrite a correct assertion or "fix" correct arithmetic. Fix: state that the real ceiling is golden×3 ×4 = 12×, and replace the catch with a relative assertion (e.g. `addScore(100)` with vs without `doubleGold` at a fixed hoard state ⇒ exactly 2× the baseline, bounded by the cap factor).

2. **`invertControls` has no observable horizontal effect and its stated catch is unreachable.** The owning resonance is `'gravity~mirror'` (L882), so the mirror mutator is *always* active when `invertControls` is. The plan moves mirror into `setNextDirection` (negates `dx`, L8333) and adds a 180° rotation (negates `dx` **and** `dy`) in the same function — the two cancel on `dx` by construction. Worse, the plan's catch (L49: force the window open, press ArrowLeft, `dirQueue` dx `+TILE_SIZE`) cannot pass: ArrowLeft → `-TILE_SIZE` (L8308) → mirror `+TILE_SIZE` → invert `-TILE_SIZE`, i.e. the queued dx is `-TILE_SIZE`, or the press is rejected outright as a reversal of the tail. The remaining observable is vertical only (Up→Down), which is partly indistinguishable from gravity's default fall. Fix: apply the inversion **before** the mirror flip (so mirror survives), or invert only the axis mirror does not touch, and rewrite the catch to assert the vertical axis (`ArrowUp` under `gravity~mirror` with the window open must queue `dy = +TILE_SIZE`) plus a horizontal no-op assertion.

3. **The determinism claim is wrong, and Feature A makes the leak worse.** Plan L23 ("delete the only resonance-era `Math.random()` call in the tick loop") versus L6030 (`shuffleFoodWeights()`'s `keys.map(function() { return Math.random(); })`), called from the tick loop at L6457 whenever `chaos_seed` is active. Feature A then halves that cadence 20→10 for `doubleGold` (L31) and adds a brand-new caller for `quantumToggle` (L34) — while the plan's own Verification §5 declares "Any `Math.random()` introduced into a seeded path is a defect." A seeded Classic run that drafts `chaos_seed` is non-deterministic today and would become twice as non-deterministic for `doubleGold`. Fix: convert L6030 to `seededRandom()`, and reword the claim.

4. **`quantumToggle`'s reshuffle half is a no-op as specified.** Plan L34 says "or call `shuffleFoodWeights()`". That function *returns* a fresh weight map (L6036) and mutates nothing; the only assignment is `chaosCurrentWeights = shuffleFoodWeights()` at L6457. A bare call therefore produces zero observable change — a green, inert implementation, i.e. exactly the v11 failure class. Additionally, the pair that owns `quantumToggle` is `mirror~chaos_seed`, so the `chaos_seed` mutator is *already* reshuffling every 20 ticks (L6456-6459) and is already displayed by that HUD path; that half is pre-existing behaviour, not a new mechanic. Fix: specify `chaosCurrentWeights = shuffleFoodWeights(); chaosShuffleTick = gameTick;` explicitly, and either state what the reshuffle half adds beyond the mutator the player already drafted, or replace that half with a genuinely new effect.

5. **`clearToasts()` in `resetWaveState()` silences the gauntlet wave-complete toast.** Plan L136/L140 mandates it from "both reset sites". `completeGauntletWave()` queues `'Wave N Complete! +pts'` with a 2000 ms duration (L5850) and then shows the intermission; the confirm handler calls `startNextWave()` (L7823), which calls `resetWaveState()` (L5873). Clearing there destroys the only feedback for completing a wave whenever the player confirms within 2 s — the common case. `resetWaveState` is a mid-run reset; the toast channel is not per-run game state. Fix: clear from `resetGame()` only, or re-queue the wave toast after `resetWaveState()`.

6. **Feature C's rescue-site list is wrong and incomplete.** Plan L99 lists L6556/L6580/L6591/L6610, but L6591 is `'Serpentine phased through an obstacle!'` and L6610 is `'Phoenix Brew resurrected!'` — neither is a "saved you" message — while the genuinely matching hazard-path save at **L6648** (`'Vampire Brew saved you from a hazard!'`) is omitted, as is the rival-path resurrection at **L6697**. Following the plan literally would ship a recap card that reports "Vampire Brew saved you from a hazard!" as the cause of death in the hazard path — the most common save path with the Vampire brew. Fix: enumerate all six rescue messages (L6556, L6580, L6591, L6610, **L6648, L6697**) as the set that must be classified as saves, and note that the true assignment count is 18, not 16 (L85).

7. **Features B, C, D and E are budgeted zero assertions, and none of them has any existing coverage.** `grep` over all 11 suites finds no reference to `drawRecapCard`, `recapData`, `cardH`, `drawHelpOverlay`, `showFoodLegend`, `toastEl`, `foodInfo` or `drawHazards`. Only Feature A ("tests (~60)", L42) and Feature F ("tests (~10)", L162) budget any. Feature D's own verification (L120) explicitly names an assertion ("assert every printed percentage equals `Math.round(FOOD_TIERS[k].weight * 100)`") that no LOC line funds, and Feature E is described as three *verified defects* on a channel `test-v9.mjs:205-213` already exercises indirectly. Shipping the two "cheapest and safest" features with zero assertions is how v11 shipped green. Fix: add explicit assertion budget for E (queue cap, clear-on-session-reset, legend routed through the queue, coalescing) and D (derived percentages/colours match `FOOD_TIERS`); state why B and C rely on screenshots alone.

## Scope assessment

Six features / ~540 LOC against v11's seven / ~705 is the right direction, and the "repair the promises the game already makes" theme is the correct organising principle after v11. Two observations:

- **The flagship is oversized relative to its risk.** Feature A is 200-245 LOC (the plan's own numbers disagree) touching the input choke point, the self-collision death path, the score funnel, hunger, the shrink advance, the snapshot and both reset sites — and it is the only feature whose *effect specs* are wrong (issues 2, 4) or arithmetically impossible (issue 1). If the cycle must absorb risk, this is where a cut lands most safely: shipping six of eight resonances (dropping `invertControls` and `quantumToggle`, the two input-mutating ones) would leave the feature coherent, remove the mirror-relocation dependency entirely, and free ~70 LOC plus the pass-2 verification pass — and the remaining six are all specifiable inside existing state. The descriptor-rewrite fallback the plan already establishes (L21) covers the two dropped ones honestly.
- **Feature F is the right thing to cut for coverage.** It is pure tuning (45 LOC) on a bank none of the other five features touch, it ships the plan's weakest verification (issue 15), and its stated remedy for charge inflation is "raise the spend costs" — a balance decision the plan itself defers to the design owner. Its 55 LOC (code + the test budget A and F alone get) buys the missing assertions for E and D (issue 7).
- **Nothing essential is missing as a prerequisite**, with one ordering exception: the mirror-flip relocation is a prerequisite for `chaosCycle` and `quantumToggle` as specified, but it is scheduled *after* `chaosCycle` (pass 2 vs pass 1). Nothing else has a cross-feature dependency; B is correctly positioned as the prerequisite for the deferred Rift Harvest.
