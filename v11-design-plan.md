# Snakes v11 — Design Plan

## Overview

Seven features selected from 28 ideas generated by 3 ideation agents (gameplay, meta/retention, polish/accessibility). Selection criteria: impact × feasibility / risk, cross-feature synergy, and coverage across all three angles. Total estimated ~705 LOC.

v10 baseline: commit `cfaf4f0`, ~8033 lines, 94-test suite. The game has 20 features across v7–v10: render scheduler, evolution, quests, visual polish, snapshots, PWA, HiDPI, calm mode, settings panel, recap card, hunter food, bounty rush, save export/import, auto-save, combo aura, portal food, golden hoard, visual feedback, input buffer, CVD palettes, meta-achievements, daily leaderboard, bomb food, combo bank, hazard zones.

v11 theme: **depth over breadth — compound with existing systems, not add new dimensions.** Every selected feature deepens an already-shipped system rather than introducing a new one. This is the cycle where hazards, hoard, combo bank, streaks, and diary become a connected web instead of parallel silos.

## Feature A — Hazard Chain Bonus

**Concept:** Eating food while standing adjacent to (within 1 tile of) a pulsing *on-phase* Hazard Zone grants a "Hazard Harvest" stacking score multiplier: +1 to the chain per consecutive hazard-adjacent eat, up to ×3. The chain resets to 0 if you eat a non-adjacent food or get hit by a hazard. Turns the existing hazard zones from pure-penalty tiles into a risk/reward lane the player *opts into* — park next to lava for big points, but one wrong tick and the phase flips to lethal.

**Why:** Hazards (v10 C) are currently pure avoidance. The combo bank and hoard already model risk/reward; hazards are the only system without an upside. Giving hazards a score upside completes the risk/reward loop and makes the hazard phase-cycle a *scoring rhythm* the player can route, not just a death timer. Cheapest possible hazard depth (score-only, no new collision, no new food tier).

**LOC:** ~70

**Scores:** Impact 4, Feasibility 5, Risk 2, Synergy 5

**Hook points:**
- `tickHazards()` L3362 — already iterates hazards each tick; add a `phase === 'on'` adjacency check vs `snake[0]` (Manhattan ≤ TILE_SIZE) to set a boolean `hazardAdjacentThisTick`.
- `isHazardCollision(pos)` L3402 — reuse its on-phase test pattern for the adjacency probe (same loop shape, different predicate: distance ≤ `radius + TILE_SIZE` instead of ≤ `radius`).
- `addScore(amount, multi)` L1800 — the `scoreMultiplier` / `effectiveHoardMult` path at L1796–L1800 is the existing multiplier injection site; chain a `hazardChainMult` there as `1 + Math.min(hazardChainStreak, 3) * 0.5` (so ×1.5 at 1, ×2 at 2, ×2.5 at 3, capped).
- Eat site L6484 (the food-eat block, after combo bonus) — bump `hazardChainStreak` if `hazardAdjacentThisTick`, else reset to 0. Emit a floater ("×N Hazard Harvest!") when streak ≥ 1.
- `checkPlayerDeath()` hazard branch L6238 — on hazard death, reset `hazardChainStreak = 0` (in addition to the death).
- `resetGame()` L2055 + `resetWaveState()` L5419 — clear `hazardChainStreak` (both reset sites, per invariant).
- Snapshot additive: add `hazardChainStreak` to `buildSnapshotObject()` L2493-area and `restoreFromSnapshot()` L2622-area (missing → 0).
- `drawHazards()` L4508 — when `hazardAdjacentThisTick && hazardChainStreak > 0`, draw a subtle gold ring around the adjacent hazard (CVD-safe; use a fixed high-contrast hue, not `foodColor` since this isn't a food tier). `ctx.save()`/`ctx.restore()` per the sub-function leak rule.

**Hazards-enabled modes only:** gated on `MODE_CONFIG[gameMode].hazardsEnabled` (same as `tickHazards`). In modes without hazards, `hazardAdjacentThisTick` is always false and the multiplier is ×1 — no-op.

## Feature B — Combo Heat → Hazard Melt

**Concept:** At combo ≥ 10, the snake's combo heat aura (v9 C, L4916) becomes hot enough to *melt* hazards: entering an on-phase hazard at combo ≥ 10 downgrades the hit from lethal to a combo-break (resets `comboCount` to 0, no death, emits a "Melted!" floater + particle burst). A pure-movement risk/reward: keep your combo high and you can cross lava once; lose it and lava is deadly again. Ties the existing combo-heat visual to a mechanical payoff and makes "maintaining combo" a defensive action, not just a scoring one.

**Why:** Combo heat aura (v9 C) and hazards (v10 C) are both visual+mechanical systems with no crossover. This is the smallest idea (45 LOC) that connects them, and it reframes the combo system: high combo isn't just score, it's a shield you actively maintain. The combo bank (v10 A) already spends combo; this lets you *protect* it.

**LOC:** ~45

**Scores:** Impact 4, Feasibility 4, Risk 3, Synergy 5

**Hook points:**
- `isHazardCollision` death path L6238 — the hazard death check inside `checkPlayerDeath()`. Before the shield check, add: `if (comboCount >= 10) { comboCount = 0; lastComboMilestone = 0; lastDeathCause = 'Melted a hazard!'; spawnParticles(wrappedHead.x, wrappedHead.y, 20, '#FFAA00'); pushTransientRing(wrappedHead.x, wrappedHead.y, 40, '#FFAA00', 400, 'ring', 3); return false; }`. The melt must slot *before* shield so a high-combo player isn't punished by also consuming their shield.
- `comboCount >= 3` aura at L4916 — extend the visual threshold ladder: at `comboCount >= 10` show a distinct "molten" tint (brighter orange-red, higher alpha cap 0.7 vs 0.5). CVD-safe via a fixed high-contrast hue; do NOT use `foodColor` (this isn't a food tier).
- `comboCount` reset sites L6406/L6429 — the melt path mirrors these (sets `comboCount = 0` + `lastComboMilestone = 0`).
- No new state, no snapshot change (reads existing `comboCount`).
- `comboHeatColor(combo)` L4916-area — extend the existing helper to return the molten variant at combo ≥ 10.

**Death save chain order (load-bearing):** melt → shield → vampire → serpentine → death. The melt is the first gate; if it fires, none of the downstream saves activate. This is intentional — melt IS the save, consuming the combo as its cost.

**Hazards-enabled modes only:** gated implicitly — `isHazardCollision` only returns true in hazards-enabled modes. In non-hazard modes, the melt branch never fires.

## Feature C — Hoard Pigment Rush

**Concept:** During the Golden Hoard, each of the 4 bonus foods in `extraFoods[]` carries a hidden "pigment" tag. Eating all 4 before the hoard timer expires unlocks a 5-second "Pigment Rush": the board tints gold, all foods (including the primary `food`) score ×3, and the rival freeze extends by 3 seconds. Converts the hoard from a passive buffet into an active eating *combo within a combo* — you have ~15s to sweep all 4, and the reward is a 5s climax.

**Why:** Hoard (v9 E) is already a timed event with a multiplier and rival freeze, but the player just idly collects. This adds an internal objective so the player *plays* the hoard. Synergizes with the `extraFoods` plumbing (v9 D), the `scoreMultiplier` path in `addScore` (v9 E), and the rival freeze (v9 E). All infrastructure exists.

**LOC:** ~75

**Scores:** Impact 4, Feasibility 4, Risk 3, Synergy 5

**Hook points:**
- `activateHoard()` L3416 — tag the 4 hoard foods with `pigment: true` when pushing to `extraFoods` at L3424 (via `generateHoardFood()` return value, or post-push iteration).
- `extraFoods` eat block L6589 — on eating an `ef.pigment` food, increment `hoardPigmentCount`; at 4, set `pigmentRushTimer = 300` (5s × 60fps ≈ 300 ticks, but use tick count: `HOARD_DURATION/3`), bump `scoreMultiplier` via a new `pigmentRushActive` flag checked in `addScore`'s `effectiveHoardMult` path (L1796–L1800), extend rival `respawnTimer` by 3s, `queueToast('Pigment Rush! ×3!')`, `queueGameEffect('flash')`.
- `endHoard()` L3429 — clear `hoardPigmentCount` and `pigmentRushTimer`; if rush is active when hoard ends, let it run its course (the rush timer is independent of `hoardActive` once triggered — design choice so the player isn't punished for triggering the rush at the last second; the rush is a reward, not a hoard sub-state).
- `addScore()` L1796 — the `effectiveHoardMult` cap. When `pigmentRushActive`, the multiplier is ×3; when `golden_food` mutator is active, cap the rush at ×2 (so Golden Age + Rush = ×4 max, not ×6 — mirrors the existing hoard+golden cap at L1797).
- Rival freeze already keyed on `hoardActive` at L6769/L6777 — extend `rivals[rii].respawnTimer += 3000` when rush triggers.
- `drawGame()` L5219 (hoard tint) — add a stronger gold tint when `pigmentRushTimer > 0` (alpha 0.12 vs 0.06, or 0.06 in calm mode).
- `animateVisuals()` timer-decay section — decrement `pigmentRushTimer` per tick (game-tick, not rAF — this is game-logic state written in the tick loop, like `hoardTimer`).
- `tickHazards()` L3362 — no change (pigment rush doesn't affect hazards; they remain lethal).
- Snapshot: `hoardPigmentCount` + `pigmentRushTimer` are additive (missing → 0) alongside existing hoard fields at L2583/L2722.
- Reset: `resetGame()` L2055 (E is Gauntlet-excluded, so `resetWaveState()` NOT needed — matching hoard precedent).
- `hasSeenPigmentRush` first-time toast (mirrors `hasSeenPortal`/`hasSeenBomb` pattern).

## Feature D — Daily Seed: Hazard Layout

**Concept:** The daily seed (already deterministic via `seedPrng`) now also seeds hazard spawn positions and phase offsets, so the Daily Challenge has a fixed, learnable hazard rhythm players can route over multiple diary replays. Non-daily modes keep RNG hazards. Turns hazards from random into a *memoizable* obstacle course in the daily mode — depth for the diary-replay loop.

**Why:** Daily seed (shipped) + diary replay (v9 G) + hazards (v10 C) are all live but disconnected. Wiring determinism is cheap and gives daily players a routing skill to grind — the same "learn the seed" mental model that makes the daily seed compelling, extended to hazards. The daily leaderboard (v10 D) then rewards hazard-routing skill, not just reflex.

**LOC:** ~50

**Scores:** Impact 3, Feasibility 5, Risk 2, Synergy 4

**Hook points:**
- `tickHazards()` spawn branch L3381 (`hazardTickCounter >= HAZARD_INTERVAL`) — when `gameMode === 'daily'`, derive spawn position from `seededRandom()` (already seeded for daily via `seedPrng`) instead of `Math.random()`. Store a `dailyHazardIndex` counter so replays reproduce order.
- `hazards.push({...})` L3390 — add a `seedOffset` field for deterministic phase offset (`HAZARD_ON_TICKS`/`OFF_TICKS` shifted by `seedOffset = Math.floor(seededRandom() * HAZARD_ON_TICKS)`).
- Daily mode config L1230 already runs the deterministic RNG; no mode-config change.
- Diary replay path reuses `resetGame` → `startGame` with the stored seed; hazards fall out of the same RNG stream.
- Snapshot unaffected — hazards already serialize at L2667; the determinism is a *spawn-time* property, not a per-tick state.
- Non-daily modes: the `gameMode === 'daily'` gate keeps `Math.random()` for Classic/TimeAttack/Snap, so their hazards stay RNG (no determinism change for them).
- **Determinism audit:** `tickHazards` currently uses `Math.random()` for spawn position. The change is: in the daily branch, replace `Math.random()` calls with `seededRandom()`. Must verify `seededRandom` is the daily RNG (it is — `seedPrng` is set in `startGame()` daily block L2256). Non-daily modes are unaffected.

## Feature E — Streak Multiplier Ladder

**Concept:** The daily streak (L2271) currently only unlocks static cosmetics (`STREAK_UNLOCKS` L1168). Extend it into a compounding economy: a streak-scaled XP multiplier (+1% per streak day, cap +30%) applied in `awardXP()` (L6879), feeding into the overcharge loop (L741/6885) and quest XP (L1502). At 7/14/30-day thresholds, grant a "streak charge" — a one-time, bankable death insurance (survive one lethal hit) usable in any mode, stored as an additive snapshot field so a resume preserves it. The charge is opt-in (player chooses to spend on death, not automatic) and one-charge so it doesn't trivialize hazards/bombs.

**Why:** Streak is the single biggest daily-return driver but its reward is static and front-loaded (cosmetics at 3/7/14/30 days, then nothing). A compounding multiplier makes every consecutive day *more* valuable, and the death-insurance charge gives a tangible mid-run reason to protect the streak. Synergizes with XP, quests, overcharge, and the snapshot engine.

**LOC:** ~130

**Scores:** Impact 4, Feasibility 4, Risk 3, Synergy 5

**Hook points:**
- Streak source: `saveManager.getInt('snake_streak_count', 0)` L2271, L2296.
- XP award: `awardXP()` L6879 — apply `const streakMult = 1 + Math.min(0.30, streakCount * 0.01);` multiplier to the XP gained. `awardXP` already computes `xpGained` — multiply there before the overcharge loop.
- Overcharge: `xpOvercharge` L741, written at L6885 — the multiplier amplifies overcharge gain automatically (it multiplies the input to the overcharge loop).
- Quest XP: `claimQuest()` → `awardXP(q.reward.xp)` L1502 — inherits the multiplier automatically (it calls `awardXP`).
- Threshold grant: extend `STREAK_UNLOCKS` loop at L2297–L2306 — at 7/14/30 days, grant a streak charge via a new `snake_streak_charges` save key (`saveManager.setInt('snake_streak_charges', count + 1)`). Use a `STREAK_CHARGE_DAYS = [7, 14, 30]` array; check on daily game start (alongside the existing streak increment at L2271).
- Charge consume: death handling in `gameOver()` L3076 — before the death is finalized, if `streakCharges > 0` and the player opts to spend (a new "Use streak charge? [Y/N]" prompt on the game-over screen, OR automatic with a toast "Streak charge consumed!"), cancel death, decrement `streakCharges`, `saveManager.set`, toast, and resume the run (`gameState = 'playing'`). **Design decision: automatic with toast** — a prompt mid-death is bad UX; the charge is the insurance, spending it IS the point. The player banks it knowing it'll auto-fire.
- Snapshot additive: `buildSnapshotObject()` L2493 — add `streakCharges` (additive, no version bump, missing → 0).
- Reset: `streakCharges` is NOT per-run (it's a persistent bank) — do NOT reset in `resetGame()`/`resetWaveState()`. It's read from `saveManager` at run start.
- Display: streak block at L4335–L4340 + `updateMenuFooter()` L2214 — show charges as "🛡×N" next to streak info.
- `checkPlayerDeath()` L6187 — the streak charge save is the FIRST gate in the death save chain (before shield): melt → **streak charge** → shield → vampire → serpentine → death. Wait — re-examine: the streak charge is a persistent meta-resource, while shield/vampire are per-run. Order by "cheapest to lose": shield (per-run, regenerates) should fire before streak charge (persistent, banked across days). **Corrected order:** melt → shield → vampire → **streak charge** → serpentine → death. The streak charge is a last-resort save after per-run saves are exhausted.

**Death save chain order (corrected, load-bearing):** melt (combo ≥ 10) → shield → vampire → **streak charge** → serpentine → death. Streak charge is after per-run saves, before serpentine (which is obstacle-specific). This preserves per-run resources first.

## Feature F — Save Corruption Auto-Recovery

**Concept:** Wrap every `saveManager.getJSON` call with a schema validator that, on parse failure or shape mismatch, quarantines the bad key to `snake_corrupt_<key>` (for user inspection/export) and restores the default — instead of silently returning the default and losing the data. Add a one-time toast on next load: "Save data issue detected — backed up corrupted keys, settings reset." The existing `exportSaveData()` (L1692) already iterates all `snake_*` keys, so quarantined keys are included in exports for manual recovery.

**Why:** The snapshot engine (L2598 `saveSnapshot`, L2622 `restoreFromSnapshot`) and export/import (L1692/L1709) are now load-bearing persistence features. A corrupted snapshot silently cleared at L2624 loses a mid-run save with no recourse; a corrupted `snake_achievements` (L1212, no validator) silently wipes all achievement progress. The `validator` parameter already exists on `getJSON` (L225) — only 2 keys use it today. This is robustness/UX, compounding with the snapshot engine and export/import.

**LOC:** ~90

**Scores:** Impact 3, Feasibility 4, Risk 2, Synergy 4

**Hook points:**
- `saveManager.getJSON(key, defaultVal, validator)` L225 — already accepts a `validator` callback but returns `defaultVal` silently on failure. Add quarantine logic: on parse failure OR validator-fail, copy the raw string to `snake_corrupt_<key>` before returning `defaultVal`. Track quarantined keys in a module-scope `Set` so the load-time toast can list them.
- `saveManager.set(key, value)` L217 — no change (this is the write path; quarantine happens on read-fail, not write).
- `restoreFromSnapshot(data, fromStorage)` L2622 — `if (fromStorage) clearSnapshot()` L2624 on bad data; before clearing, quarantine so the run isn't lost forever. The quarantine is in `getJSON` if the snapshot is read via `getJSON`, but `restoreFromSnapshot` reads raw — add an explicit `quarantineKey(SNAPSHOT_KEY)` call before `clearSnapshot()` on validation failure.
- `exportSaveData()` L1692 — `Object.keys(localStorage).filter(k => k.indexOf('snake_') === 0)` L1695 — quarantined keys are automatically included (they're `snake_corrupt_*`).
- `importSaveData(file)` L1709 — on import, validate each key; quarantine failures with a toast listing which keys were rejected.
- `queueToast(message, duration)` L6955 — reuse for the "corruption detected" notification. Fire once on load if `quarantinedKeys.size > 0`.
- `renderSettings()` L1621 — add a "Restore Backed-Up Data" button if any `snake_corrupt_*` keys exist. The button calls `exportSaveData()` (so the user can download the corrupted keys for manual inspection) — no separate restore flow (corrupted data is by definition untrustworthy).
- Module-scope `quarantinedKeys = new Set()` — populated during load, read once for the toast, then can be cleared (it's load-time only).
- **Quarantine prefix:** `snake_corrupt_` — must use this exact prefix so the quarantine logic itself doesn't re-quarantine (a `snake_corrupt_*` key read-fail should NOT create `snake_corrupt_snake_corrupt_*`). Add a guard: `if (key.startsWith('snake_corrupt_')) return defaultVal;` (no re-quarantine).

## Feature G — Input Buffer Visualization

**Concept:** Show a subtle directional chevron indicator at the snake's head when the 2-deep `dirQueue` (L261) has pending turns queued, so players can see that their buffered input was registered — especially important at high speeds where a queued turn might feel "eaten." The indicator draws a small semi-transparent arrow offset 4px from the head in the queued direction, fading in when a turn is buffered and out when consumed. Compounds directly with the Input Buffer Queue (v10 G) and the existing touch swipe indicator (L4161–4166).

**Why:** The Input Buffer Queue (v10 G, L261, L3784–3793, L6148–6152) is the newest input feature and a core feel improvement, but it's invisible — players at high tick speeds can't tell if their second queued turn registered or was dropped by the 2-cap (L3793). A visual confirmation closes the feedback loop and makes the buffer feel intentional rather than buggy. The touch indicator (L4161) already proves the pattern works.

**LOC:** ~50

**Scores:** Impact 3, Feasibility 5, Risk 1, Synergy 5

**Hook points:**
- `let dirQueue = []` L261 — the buffer; read its length and contents for the indicator.
- Tick consumption site L6148 — where the queue is shifted; the indicator fades out here (conceptually — the rendering reads `dirQueue.length` each frame, so when it drops to 0/1, the indicator updates automatically).
- `function setNextDirection(newDx, newDy)` L3784 — the push site; no explicit fade-in needed (rendering reads `dirQueue.length` live).
- `function drawSnake(t)` L4898 — draw the chevron after the head segment, using `snake[0]` position. For each pending entry in `dirQueue` (max 2), draw a chevron at increasing offset (4px, 8px) in the queued direction. Alpha = 0.6, CVD-safe fixed color (white or high-contrast yellow). `ctx.save()`/`ctx.restore()` per the sub-function leak rule.
- Touch swipe indicator L4161–4166 — the existing pattern for a fading directional indicator at the head; reuse the `touchIndicatorTimer` alpha approach (but `dirQueue`-driven, not timer-driven — the indicator is visible whenever `dirQueue.length > 0`, no timer needed).
- `calmModeEffective()` L326 — gate the indicator off in Calm Mode (it's a motion cue). In calm mode, the buffer still works, just no visual.
- `animateVisuals(timestamp)` L4023 — no per-frame state needed (the indicator is static while `dirQueue` is stable); it's drawn in `drawSnake` which runs in the tick loop. But `drawSnake` is also called from rAF via `drawGame` — the indicator renders correctly either way since it reads `dirQueue.length` live.
- No snapshot change (reads existing `dirQueue`).
- No reset change (reads existing `dirQueue` which is already reset in `resetGame`/`resetWaveState`).

## Implementation Order

Features have minimal cross-dependencies but share the hazard and addScore paths. Suggested order (least risk first, building up):

1. **G. Input Buffer Visualization** (~50 LOC) — pure rendering, reads existing state. Self-contained, lowest risk. Test first.
2. **F. Save Corruption Auto-Recovery** (~90 LOC) — robustness layer on existing saveManager. No game-logic change. Safe.
3. **D. Daily Seed: Hazard Layout** (~50 LOC) — determinism wiring in `tickHazards`. Small, isolated to daily mode.
4. **A. Hazard Chain Bonus** (~70 LOC) — new multiplier in `addScore`, adjacency check in `tickHazards`. After D so the daily hazard determinism is stable.
5. **B. Combo Heat → Hazard Melt** (~45 LOC) — death-path branch in `checkPlayerDeath`. After A so the hazard-adjacency and hazard-death paths are both stable.
6. **E. Streak Multiplier Ladder** (~130 LOC) — XP multiplier + death-save chain. After B so the death save chain order is settled (melt → shield → vampire → streak → serpentine).
7. **C. Hoard Pigment Rush** (~75 LOC) — hoard internal objective. Last so the `extraFoods` eat block and `addScore` multiplier path are stable from A/B.
